# Database And Hosted Migration Guidelines

Use this when changing schema, RLS, hosted auth, timer/event writes, or migrations.

## Schema Sources

- Local schema history lives in the ordered SQL files under `packages/db/migrations`. `001_init.sql` is the base; later numbered migrations add tags and Live Activity delivery state. The setup script applies every SQL file in filename order.
- Hosted Supabase-only migrations live in `supabase/migrations`.
- `integration_tokens` is server-only authentication material: hosted schemas must enable RLS, expose no client policies, and grant no table privileges to `PUBLIC`, `anon`, or `authenticated`.
- Hosted deployments must run all required Supabase migrations before the Vercel code that depends on them is deployed or smoke-tested.

## Hosted Migration Checks

Before declaring hosted auth/timer/event changes ready, verify:

- `activity_events.client_event_id` exists when mobile event idempotency is deployed.
- indexes required by the deployed code exist.
- any new health audit columns exist before HealthKit imports are tested.
- `categories.icon` and `categories.starter_key` (with the partial unique index `categories_workspace_starter_key_idx`) exist before a server that reads activity icons or seeds starter activities is deployed.
- Activity (category) writers share one lock order: the per-name advisory locks automatic creation uses (`lockActivityNames` in `automatic-category-service.ts`, deduplicated, lower-cased, sorted — the starters route's Commute-then-Sleep order), then the workspace row `FOR NO KEY UPDATE`, then the activity row `FOR NO KEY UPDATE` (never `FOR UPDATE`: capture holds key-share locks on activities it references while it waits for a name lock). Create and rename lock the new name; Restore locks the archived name and its starter's name, comes back unpinned whatever else the request asks, and drops its `starter_key` if a recreated starter holds it. `npm run validate:starter-activities-db` (CI) covers the PATCH/capture/starters ordering, rename versus automatic creation and the restore key collision on real Postgres. The legacy `POST /api/entities` `category` path goes through `createCategory` (409 `name_taken` on a clash).
- `places.role` (check `home`/`work`, partial unique index `places_workspace_role_idx` on `(workspace_id, role)`) exists before a server that reads place roles is deployed: every place-name read path selects it.
- `places.archived_at` (`timestamptz`, null = active; `supabase/migrations/202610210001_place_archive.sql`, local `packages/db/migrations/016_place_archive.sql`, mirrored in `001_init.sql`; Archive place, location v3 PR 15, PRD D19 A10) exists before a server that reads it is deployed: `getPlaces` (bootstrap, `/api/places`, event normalization) leaves archived places out and names the migration when the column is missing, so without it bootstrap fails. Replay keeps an archived place (and accepted learned places linked to it) in its catalogue with `archivedAt`, and the engine matches it only to evidence from before that moment (a geofence hint naming it afterwards names no place), so replayed history keeps its visits, blocks and Review cards and no new visit matches it. `places.matching_starts_at` (same migration; null = all evidence) is set on a place created into a Home/Work slot with Replace when it archived the old one, and the engine matches that place only from then, so it never takes the old place's past visits; moving a role to a place that already existed leaves it alone. The v2 emitter's trusted-place reads keep an archived place's own settings for those pre-archive stays. Archived places leave nearby saved places on evidence, search, role assignment (an archived place never takes a role or counts as an implicit Home/Work) new Review place picks, saved or learned (a card that already names one still confirms), and executable automation rules (`getNormalizationContext` drops a rule whose place is archived; it is still exported); past blocks, review items, Reports and exports keep them (they join by id). `setPlaceArchived` (POST `/api/places/archive`) archives with the role cleared or restores without one, first taking every member's location owner lock (`lockLocationOwnersForArchive`, 10 s lock timeout, 409 when busy) so no replay reads the old catalogue across it; Replace takes the same locks first in its transaction; `assignPlaceRoleWith({ archivePrevious })` archives the previous holder in the same step only within 300 m of the new place ("Replace the old place"). No RLS change.
- `users.goals_revision` (`bigint not null default 0`; `supabase/migrations/202610120002_user_goals_revision.sql`, local `packages/db/migrations/012_user_goals_revision.sql`) exists before a server that reads it is deployed: bootstrap selects it (`user.goalsRevision`) and names the migration when it is missing, and every goal change in `PATCH /api/profile` bumps it in the same row update and replies with the stored goals and revision (`goals`). Web Settings orders goal copies by it instead of client clocks (UIA-309). No RLS change: the existing `users` policies cover it.
- `categories.counts_toward_goal` (`boolean not null default true`; `supabase/migrations/202610110001_category_counts_toward_goal.sql`, local `packages/db/migrations/010_category_counts_toward_goal.sql`) exists before a server that reads it is deployed: every category read selects it, and bootstrap names the migration when it is missing. The migration switches off the Sleep starter and any activity named Sleep only in the run that adds the column, so a rerun never undoes a person's choice. No RLS change: the existing `categories` workspace policies cover it. Goal progress (Today's goal frame, Reports' `dailySeries[].goalSeconds` and the iPhone goal streak) leaves out activities with `false` through `packages/shared/src/goalCounting.ts`; totals never do. Bootstrap's `categories` hold only active activities, so bootstrap also returns `goalExcludedCategoryIds` (every activity, active or archived, with `false`); clients merge it with `withGoalExclusions`, where an active activity's own flag wins. `POST /api/reports/summary` (iPhone Reports) adds each bucket's covered `goalSeconds` and the merged `goalIntervals` behind it without the running entry (both from the same column) (optional in `ReportSummarySchema`, so older phones ignore it). `createCategory` defaults an omitted value to false for a name that is Sleep (`defaultCountsTowardGoal`); linking an activity to a starter never changes it.
- `user_session_fences` (`supabase/migrations/202610120001_user_session_fences.sql`, local `packages/db/migrations/011_user_session_fences.sql`: user id → reset time, cascade-deleted with the user) exists before a server with Forgot password is deployed: `createSession` (inside a transaction) locks the user row `for share`, then reads it in a separate statement and refuses a sign-in authenticated at or before the recorded reset, so without it every sign-in fails. A password reset upserts it (with `clock_timestamp()` taken after the lock, and `greatest` so a fence never moves back) and revokes `auth_sessions` in one transaction under the user row's `for update` lock, before and after the password change, and fails closed when the user has no row. Hosted: RLS on, no policies, all `anon`/`authenticated` grants revoked (server-only; a user's JWT cannot clear or move their fence) — checked by `npm run validate:session-fence-security`.
- `users.log_trips_automatically` (`boolean not null default true`; "Log trips automatically", PRD D19 A4; `supabase/migrations/202610170002_log_trips_automatically.sql`, local `packages/db/migrations/015_log_trips_automatically.sql`, mirrored in `001_init.sql`) exists before a server that offers the switch is deployed: `PATCH /api/profile` writes it (bumping `goals_revision` in the same row update, which orders the switch for clients as it orders the goals), while bootstrap (`user.logTripsAutomatically`) and the Review-mode emitter read it through `to_jsonb(users)`, so a database without it shows the switch off and logs no trips automatically rather than failing. No RLS change: the existing `users` policies cover it.
- `location_name_patterns` (learned names, PRD D19 A8; `supabase/migrations/202610170001_location_name_patterns.sql`, local `packages/db/migrations/014_location_name_patterns.sql`, mirrored in `001_init.sql` for the base profile) exists before a server that reads it is deployed: every `v2_review` replay reads it for its candidates and every location Review decision may write it, so without it location replay and confirmation fail. One row per (workspace, user, pattern, band): `pattern_key` is a SHA-256 of the workspace and the item's pattern (a saved/learned place, a 150 m cell, a Move's ends and mode, a round trip's origin, turnaround cell and mode), never a raw place ID or cell; `name` and `category_id` the person's own, `uses` counting the name and `category_uses` the activity separately; `auto_log_opt_out` for PR 11. The migration also adds `idx_segment_evidence_commute_lookup` (route links by commute) for the round-trip turnaround read. Hosted: RLS on with the owner-only location policies (`user_id = auth.uid()` and workspace member). Exported with the workspace (`export-service.ts`, `export:workspace`); deleted with the workspace or user (cascade).
- `idx_places_geography` (GiST on `(ST_SetSRID(ST_MakePoint(longitude, latitude), 4326)::geography) where latitude is not null and longitude is not null`; `supabase/migrations/202610210003_place_geography_index.sql`, local `packages/db/migrations/018_place_geography_index.sql`, mirrored in `001_init.sql`; places at scale, location v3 PR 16): `NEARBY_SAVED_PLACES_SQL` (Location evidence's nearby saved places) uses exactly this expression in its `ST_DWithin`, so keep the two identical. Performance only; checked by a plan test in `place-role-service.postgres.test.ts`.
- `activity_events` and `time_entries` (hosted, `supabase/migrations/202610170003_owner_only_event_entry_writes.sql`, owner decision 17 Oct 2026): workspace members read each other's rows ("workspace members can read"), but only the row's own user inserts, changes or deletes it ("users can write own rows": `user_id = auth.uid()` and workspace member, as the location tables), and the same check refuses handing a row to another user or moving it into a workspace its user is not a member of (a move between two of the user's own workspaces is allowed, as for location rows). The server connects as the tables' owner, so it is unaffected; no server or client change depends on it. Checked by `npm run validate:event-entry-rls` (signed-in client as Supabase's `authenticated` role, two members of one workspace and an outsider; entry tags too). `time_entry_tags` follows its entry (`202610170004_time_entry_tags_owner_writes.sql`): members read a link whose entry and tag are in its workspace, and only the entry's own user adds or removes its tags; the earlier policies' workspace comparisons were always true inside their subqueries and now name the link's own columns (the composite foreign keys already kept them in one workspace).
- RLS policies still allow expected workspace-member reads, and writes where the table is shared (catalogue data); user-owned tables (location, events, entries) are written only by their user.
- One `pg` client (a `pool.connect()` client or a `withSyncTransaction` client) runs one query at a time: never `Promise.all` queries on the same client. `pg` queues them, logs "Calling client.query() when the client is already executing a query is deprecated", and pg@9 will refuse them. Await them in turn (it is no slower on one connection); independent reads that need no shared snapshot may use the pool's `query()`, which takes a connection each. `review-presentation-service.test.ts` checks the Review presentation for overlap.
- `DATABASE_URL` matches the Supabase pooler string that works in Vercel.

## Timer/Event Writes

- Timer start/stop should be transactionally event-first: insert `activity_events`, then create/close `time_entries` when the event is high-confidence.
- Timer writes must scope by both `workspace_id` and `user_id` where active user state matters.
- Entry-scoped Stop updates only its exact active `time_entries.id` and bypasses the coarse per-user advisory timer lock. Keep a transaction-local 2-second row-lock deadline inside a 5-second statement deadline and map bounded contention to retryable `timer_busy`; current-scope Stop, starts/replacements, and Health sleep serialization retain the advisory lock where required.
- Check `client_event_id` receipts before the timer lock and again inside the transaction. The existing unique index remains the final replay/race boundary; do not add a redundant Stop receipt table.
- Category-only and uncategorized entries are valid if approved by product rules; do not reintroduce project requirements in service logic.
- Add regression coverage for start, stop, manual entry, duplicate `clientEventId`, and cross-workspace isolation.
- For lock-strategy changes, retain a gated disposable-database test with two real Postgres connections: one holds the user's advisory lock while the other completes an exact entry-scoped Stop. Verify the hosted `activity_events.client_event_id` unique index before staging smoke tests.
- User-created overlaps require no exclusion constraint or overlap-uniqueness index on `time_entries`. Technical uniqueness belongs to source identifiers such as client event IDs, external Health samples, location segments, and Review mutation receipts.
- `time_entries.user_edited_at` is the protection boundary for automatic Health sleep reconciliation. Every explicit entry update must set it; automatic same-source sleep-window extension may update only rows where it is null and must preserve the stable entry id and metadata.
- `places.role` moves only through `assignPlaceRoleWith` (`apps/web/src/lib/place-role-service.ts`): one transaction locks the current holder and the target in id order with `FOR NO KEY UPDATE` (so swapping Home and Work from both sides cannot deadlock, and entry/segment key-share locks are not blocked), clears and optionally renames the old holder, then sets the target. A racing move that hits the unique index returns a retryable `409 place_role_conflict`. `apps/web/src/lib/place-role-service.postgres.test.ts` covers this against a disposable database (`DAYFRAME_PLACE_ROLE_TEST_DATABASE_URL`, run in CI).
- `time_entries.place_label` is the bounded one-time location name for a confirmed unknown visit. The database check permits `place_id` or a trimmed 1–120-character `place_label`, never both. Explicit saved-place edits clear `place_label`; ordinary time/category/description/tag edits preserve it. Deploy `supabase/migrations/202608120001_time_entry_place_label.sql` before code that selects or writes this column.
- Deploy `supabase/migrations/202608010001_health_sleep_session_reconciliation.sql` before server code that queries `user_edited_at`. Its historical backfill intentionally protects all previously changed Health sleep rows. It does not merge or delete historical duplicates.
- Reporting coverage must clip intervals to the requested range and use a gaps-and-islands union. Do not infer covered time by subtracting pairwise intersections.

## Session And Personal-Report Reads

- Root layout/page consumers must share one request-scoped optional-session result. Do not create separate `cache()` wrappers or a cross-request user-session cache.
- Optional session resolution may return anonymous state for no cookie or an explicit `401` authentication error only. Database, SQL, configuration and programming errors must propagate to the normal server error path.
- Bound `auth_sessions.last_used_at` writes with an age condition; ordinary page/API polling must not update the row on every read.
- Bound `integration_tokens.last_used_at` writes with the same age-conditioned principle. A scoped high-frequency fingerprint consumer must authenticate and update its usage timestamp periodically without creating one MVCC row write per poll.
- Personal Reports queries must scope `time_entries` by both `workspace_id` and `user_id`, including daily series and workspace-qualified joins. Add a two-user/same-workspace regression whenever report query architecture changes.

## Migration Safety

- Prefer additive migrations for repair work.
- Keep legacy nullable fields until data migration is explicitly approved.
- Do not drop historical data or integration tables without an export/safety decision.
- `ON DELETE SET NULL` runs as one update per referencing column, and each update fires that table's `before update` triggers. An owner-link trigger that checks several place columns (`dayframe_commute_owner_links` on `commute_segments.from_place_id` / `to_place_id`) rejects a row whose other column still names the row being deleted, so the whole delete rolls back. Deleting a parent such rows can point at twice must clear every reference in one update first, inside the delete's transaction (`deletePlace`), and the delete needs a Postgres validator on the real schema: a mocked query cannot see triggers (location v3 bug 6, `validatePlaceDeleteWithSamePlaceJourneys`). A delete or update that touches location rows outside the location services must take the same per-user owner advisory lock first (`pg_advisory_xact_lock(hashtext(workspace), hashtext(user))`): replay locks stays before journeys, and the reverse order deadlocks with it.

## Review automation storage

SQLite v5 adds account-owned per-source mutation effects and backfills v4 outbox rows transactionally; v6 adds contention, reconciliation, resolution, and validated-acknowledgement metadata without replacing immutable envelopes or effect anchors. Neither migration removes queued intent or compatibility columns. Two-source merge intent must reserve both IDs atomically. Postgres already has the boundary fields, `commute_segments.max_gap_seconds` and Review mutation receipts; changing these policies needs no new Postgres migration. The max-gap column means maximum internal observation gap (ceil to integral seconds), not total commute duration. Verify existing columns, receipt uniqueness and indexes in staging before smoke tests; do not fabricate bounds for old rows. Keep same-source Sleep lookup plus insertion under its existing user lock, and preserve `user_edited_at` protection.

SQLite v7 is an additive migration inside the existing Review-store exclusive
transaction. It adds owner/backend-bound Review-presentation context and
terminal-source evidence only; it does not rename the database, rewrite queued
request JSON, alter old UUIDs/hashes/anchors, or add a hosted migration. A
context is a bounded, whitelisted display snapshot, not a second canonical
entry store. A capped bootstrap or evicted display context cannot prune an
effect. Retire an acknowledged envelope only after every affected source has
explicit terminal status and every receipt-linked entry is current in the
existing Dashboard cache or explicitly `missing`; prove that transaction and
v4/v5/v6-to-v7 rollback/reopen path against a disposable SQLite database.

## Sync recovery schema and transaction checks

Apply `supabase/migrations/202610050001_location_motion_activity.sql` to staging before the Preview that accepts Motion & Fitness evidence, and to production before that server deploys and before any phone build that sends `motion_activity` (the clean/local migration is `packages/db/migrations/007_location_motion_activity.sql`, folded into `001_init.sql`). It replaces the `location_evidence` kind check under either name (local auto-named, hosted `location_evidence_type_check`) to admit `motion_activity`, and adds `location_evidence_motion_coordinate_free`; no row changes. Server code that accepts motion must not deploy before it: those inserts would fail and retry. The phone uploads motion only in batches of its own, so a server without this change refuses just those batches (the phone marks them rejected and that motion is lost) while location batches continue.

Apply `supabase/migrations/202609040001_health_sleep_resolution_link.sql` to staging before the sync-server Preview. The corresponding clean/local migration is `packages/db/migrations/006_health_sleep_resolution_link.sql`. It adds a nullable, indexed, server-owned Sleep resolution link with delete-to-null behavior; it performs no data repair. Production application requires explicit release approval and this migration before deploying the dependent code.

Run `npx tsx scripts/validate-sync-transactions.ts` with an explicit disposable local `*_test` DATABASE_URL, plus the Review and Location database validation commands. Check both PostgreSQL 16 fallback and the deployed PostgreSQL 17 transaction pooler. Connection destruction and database lock release are separately measured: a disconnected PostgreSQL 16 active query may remain until its statement guard fires. Never use a Promise race as a substitute for releasing/destroying the checked-out client, and never return a connection with uncertain rollback health to the pool.
