# Component Guidelines

Use this when working on frontend components.

The contracts below describe the shipped components. The approved Dayframe Blocks direction (see `docs/brand-style-guide.md`) replaces some of them, for example the former circular category markers (now blocks, X3) and soft calendar fills. Each surface changes only in the redesign PR that migrates it, and that PR updates the matching contract here.

## Component Structure

- Keep components focused on one responsibility.
- Prefer existing UI primitives and local component patterns.
- Keep data fetching, mutations, and presentation responsibilities clearly separated.
- Use accessible labels, semantic HTML, and keyboard-friendly controls.
- Keep Dayframe timer surfaces category/task-first. Avoid exposing projects/clients in primary timer UI.
- Mobile running Stop is accepted after its account-owned local Stop intent persists, then the existing `ActiveTimerEditSheet` remains the sole exit-animation owner. HTTP delivery never owns dismissal. Idle Today reserves no Stop-status copy row: the idle card shows `NOTHING RECORDING`, `What are you working on?` and its `Start a block` and `Add past time` pills, and the quick-start mosaic follows the card. Retryable Stop delivery stays in the background with no spinner, progress, modal, blocking alert, header sync icon or loading-driven reflow (the quiet connectivity slot shows only confirmed offline and a brief back-online check); a permanently rejected Stop badges the account avatar and opens Settings › Sync help. Reduce Motion uses the existing sheet/layout path.
- On web, Today and Timeline must consume the one timer runtime mounted by `AppShell`. Route components must not mount an independent active-timer poll, store, API client, mutation queue, shortcut handler or manual-entry owner; navigation between those routes must preserve the same optimistic state and active-entry identity.
- Keep the persistent web timer on one explicit measured track: a flexible `minmax(0, 1fr)` task compound control, bounded Category and time tracks, a stable Play/Stop slot, and one final icon-action slot where idle Plus becomes running More. Idle/running swaps must preserve outer geometry; compact layouts may reflow the task field to its own row but must not shrink or overlap the remaining actions.
- Web Description Suggestions (command timer, Add time, the shared quick editor) have two sources. With the field empty they show the bootstrap's contextual `taskSuggestions` (top 6, capped at 5 visible) unchanged. Once the owner types, they search `taskSuggestionCandidates` — the bounded pool of the 150 most recently used distinct Description/Activity/tag variants from the last 26 weeks — through `searchTaskSuggestions` (`lib/task-suggestion-search.ts`), which ranks with the shared Recent match tiers (exact, prefix, word start, substring; case-insensitive, whitespace-normalised; then owner-typed before Review-confirmed visits, score, uses, recency) and keeps the 5-row cap. Never filter a typed query against `taskSuggestions` alone: a recent but rarely used Description sits outside the contextual 6 and would never match (13 Oct 2026, "App testing"). `taskSuggestions` keeps its size and meaning for older clients; a cached bootstrap without the pool falls back to searching the contextual list.
- Manual-entry Suggestions must reuse timer suggestion ranking and metadata without invoking timer start. Selecting one fills the manual draft's Description, Category, and Tags. Cap the visible result set to a documented number of complete content-safe rows; never force a two-line title/metadata row into the generic 44 px touch minimum or crop a partial final row. Its Tags/Suggestions surfaces remain out of flow, anchor to their actual triggers, and must not require scrolling the dialog merely to reveal the options.
- Add time must reuse the timer Category option treatment rather than a separate native select. Date/time controls retain click-to-select behaviour and use a Dayframe-owned calendar/time surface when the opened browser-native picker cannot be themed; styling only the closed native field is not sufficient evidence. Dialog child surfaces must preserve the dialog's rounded silhouette without forcing floating pickers back into a clipping container.
- Timer-owned Suggestions, Tags, Categories, and start-time surfaces must use the shared floating-surface treatment and escape the timer panel's clipping boundary. Keep their lists internally scrollable, their triggers visually connected, and phone-width variants fully inside the viewport; do not substitute a scrimmed modal for an anchored timer editor.
- `CategoryPicker` owns contextual category creation for the idle/running web timer, Add Time, Timeline List entry editing, and Calendar create/edit. Every create-enabled instance portals its panel outside the editor's scrolling content: use the nearest native `dialog` root when one exists and `document.body` otherwise. Match the category field width, prefer a 6px below-trigger gap, flip above when required, clamp to 12px viewport gutters, recalculate for panel/trigger resize plus page/visual-viewport scroll, resize and zoom, and keep only the panel internally scrollable with a 220px maximum. Opening the list or Create state must not change the surrounding editor's bounds, `scrollHeight`, or `scrollTop`; all portalled category surfaces remain inside the editor's outside-pointer, blur, Tab, focus-trap and Escape interaction boundary. Closed fields and list options show the category's circular, borderless, shadowless colour dot. The final option swaps the list for a bounded inline editor without mounting a nested form: place the accessible colour-dot action inside the leading edge of the Category name compound control instead of adding a separate Colour row, preview the same deterministic automatic colour the server will assign, allow an optional choice from all 30 canonical palette colours in the shared five-column order, and keep the colour palette in its own viewport-clamped floating surface so neither editor nor category panel reflows. Create is a standalone workspace catalogue mutation: send the trimmed name plus only an explicitly chosen palette key, keep `isPinned=false`, publish the returned row to shared bootstrap state, then select it in the local draft. Never submit, dismiss, start, stop, restart, save, or reset the surrounding entry; Description, Tags, dates and times remain under their existing owner, while the category survives later draft discard. Block blank and case-insensitive duplicate active names on both client/server boundaries; failure retains name, chosen colour, draft and focus for retry. Enter belongs to category Create; Escape closes Colour, then returns to the option list, then the trigger; arrow/Home/End navigation includes Create and colour-grid navigation; phone widths keep a 12px viewport gutter plus 44px targets. Reports, Review, Places and Automations must not opt into contextual creation.
- `CategoryPicker` also owns its create-state visual anatomy across hosts. Use 14px/650 for the embedded heading and actions, 12px/650 for the Name label, and 14px/400–500 for input and option text. Centre the 20px create swatch in a 44px leading action inside the field's 2px perimeter, producing a 14px visible edge inset and 24px centre offset. Its final list action uses a separate 1px divider inset 12px with 6px clearance before the rounded action surface; it must not use the action's border or inset shadow. Timer and compact-editor rules may style only their direct option rows, never every descendant button or the shared create form.
- The running start-date/time editor is content inside the persistent timer form, never a nested form. Enter and pointer Save must call the same direct update path, prevent outer timer submission, update elapsed state immediately, and persist after bootstrap reconciliation. Calendar/clock affordances may remain pointer-clickable but must use `tabIndex=-1` when the segmented native date/time control already provides the editable keyboard stops.
- Web date selection uses `DayframeCalendar`: a stable six-week Monday-first grid (owner decision D4, 14 Oct 2026) with muted, selectable adjacent-month dates, today in coral text (`aria-current="date"`, the chosen day's fill wins), days outside `min`/`max` dimmed and never chosen (`aria-disabled`, still reachable by keyboard) with Previous/Next month disabled past them, and one tab stop moved by the arrow keys (←/→ a day, ↑/↓ a week, Page Up/Down a month clamped to its last day, Home/End the week's Monday/Sunday; moving past the month turns the page). Finished blocks' dates (quick editor, List inline edges) and Add time stop at today (D2); Calendar navigation has no limit. The day cap also holds however a finish is reached: the quick editor refuses a changed finish on a day after today (a typed time or a longer duration carried past midnight) while leaving an unchanged one alone, and Add time defaults to the hour ending now when Calendar shows a later day and refuses a Start or Finish after today. Each opening of a picker shows the chosen day's month; a key that doesn't move (Home on a Monday) leaves no focus request behind. Date-time consumers add their own typed time control; date-only consumers must not fork the calendar geometry. At phone width (≤560 px) `DatePickerPopover` is a bottom sheet (`is-sheet`, every day a 44 px target, scrolling inside on short screens) over a scrim just under its own layer: grabber, its title and a 44 px ✕, Today · Yesterday, the grid and a full-width neutral Done; a day tap or quick pick only changes a draft that each opening seeds from the value, Done saves it, ✕/Escape/a press on the scrim keep the old date (D1/D6). On desktop a click still picks at once (D5). The phone sheet takes focus (the grid's tab stop) and keeps Tab inside it; a press on its scrim closes it unsaved (the scrim carries the quick editor's nested-surface marker, so the editor behind never treats it as an outside press). Add time's date-and-time picker shows the same title and ✕ at phone width, and its Done is neutral (`--foreground`), as every date sheet's; its ✕ closes the picker but, as leaving the field always has, keeps a typed time that is complete. Date-time consumers add their own typed time control; date-only consumers must not fork the calendar geometry.
- Reports filter disclosure content is a floating surface, not in-flow expansion. Categories, Tags, Place, Source, and More filters must preserve the report layout below them, use bounded internal scrolling, and keep URL-backed multi-selection semantics.
- Web workspace management uses one compact selector with immediate switching; Rename and New workspace reveal only their relevant form. Profile-menu workspace rows use the same flat, fill-led menu treatment as Settings and Sign out, without per-row elevation.
- Category identity uses small rounded-square block markers (X3: `--activity-marker-radius` on web, `activityMarkerRadius` on iPhone), never circles. Colour-choice controls must keep an accessible target while the visible swatch stays a borderless, shadowless block; selected state comes from focus/selection treatment rather than changing the swatch shape. Category Save is text-only and Edit uses a pencil.

- Server-rendered web Calendar, List and Reports never format a browser-local value on the server (Vercel renders in UTC; React #418). Calendar's server render and hydration pass draw the frame only — zoom, axis, day headings (weekday, date), "–" totals and an empty grid — and `CalendarReview` adds the positioned blocks, Review spans, now line and pill, day totals and the opening scroll once `useIsHydrated()` is true; the List (`EntriesTable`) likewise adds its day-grouped rows after hydration (the scrollers carry `aria-busy` until then). - Command timer autosave rules (stale-tab report, 13 Oct 2026: a second window wrote "BAU" back over "app testing"). **A tab saves only what its own user edited, relative to the server copy that edit was based on.** The runtime keeps a per-field *base* (`canonicalTimerDraftRef`, exposed as `timerDraftEdited`): for a field the user has not edited it is the newest server copy; for an edited field it is the copy the edit started from. "Edited" compares as the server stores it (`timerDetailEquivalent`: description trimmed, empty activity as none, tags by normalized name in any order), so a stray trailing space, tag case or order is never an edit. (1) The bar autosaves only while `timerDraftEdited` is true, never because a newer server copy differs from what it shows; an untouched tab adopts every newer field on refresh and sends nothing. (2) A newer copy of the same block is reconciled field by field (`reconcileTimerDraftWithBase`): an untouched field takes the server's value when the server changed it and is left exactly as typed otherwise; an edited field keeps the edit, and keeps its old base when the server changed that field too. (3) Every details PATCH from the bar (autosave, the outgoing block's save before a switch, the save after a Start's POST, Stop's details, the start-time editor, the keepalive flush on leaving the shell) sends only the edited fields plus `expectedDetails` (each field's base value) and never `placeId` or `startedAt` it did not change. The server refuses it with `409` and the current block when a sent field has changed since (`detailsChangedSince`, row locked `for update`); the tab then shows the server copy as its draft and base and says "This block was changed in another window or device, so its latest details are shown." A Stop whose details are refused still stops the block, with the other change. `expectedDetails` is optional: mobile and older clients are unchanged. A same-tab editor save (the quick/inline editor on Today, Calendar, Reports: `updateActiveEntryFromCalendar`) owns the base the same way: the fields it writes become the base when it is sent (restored if it fails), so typing in the bar while it is pending is saved against the editor's values, never a false 409. A switch or quick start whose outgoing edit is refused still switches and keeps the alert ("Switched. The block you left was changed in another window or device, so your edit to it was not saved."): `beforeStart` hands the notice to the Start, which shows it instead of clearing the error. (4) While a details save is in flight, a server copy of the block that is not newer than the shown one (a period load or refresh requested before the PATCH, answered while it is pending) cannot replace it (`keepCurrentActiveOnTie`), so the acknowledgement never lands on stale details. (5) Discard ("Discard running block") never sends an optimistic id: it deletes the real block the Start's POST returned (`startHandoffsRef`), or waits behind an in-flight Start (`whenIdle`) and then deletes the real block, or nothing if the Start was rejected.
